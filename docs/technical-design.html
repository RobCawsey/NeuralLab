01

Two algorithms, one instrument

Most neural-network teaching material shows you a diagram of backpropagation and then hands you a library that does it for you. The diagram and the library never meet. NeuralLab closes that gap: the arrows in the diagram are the numbers on screen, and the numbers on screen come from the code that is actually training.

Evolab made a genetic algorithm watchable by pausing it between operators and showing each one acting on real genomes. NeuralLab does the same thing twice, because there are two algorithms here and they fail in opposite ways:

  • The multilayer perceptron is supervised. It is told the answer, measures how wrong it was, and pushes that error backwards through the network. Its failures are numerical — gradients that vanish, steps that overshoot, a model that memorises its training set.
  • The Kohonen self-organising map is unsupervised. Nobody tells it anything. A grid of nodes competes to be nearest each sample, and the winner drags its neighbours with it, so the grid ends up folded through the data like a net. Its failures are structural — a map that stays twisted, a schedule that cools too fast, a lattice that tears.

Putting them in one app is not a convenience. It is the last lesson: the same dataset, seen once through a boundary the network was told to find and once through a structure it found on its own.

The one rule. Every screen that explains the algorithm is driven by the algorithm. Not an animation of backprop — backprop, paused. If a panel would need its own copy of the maths to draw itself, the panel is wrong, not the architecture.

Who it is for

Somebody who can program, has heard of neural networks, and has never seen one learn. They should be able to open the page, press one button, and watch a network go from a scribble to a boundary in under ten seconds — and then be able to break it on purpose.

What it is not

  • Not a framework. No autodiff, no graph compiler, no GPU kernels. Every gradient in this project is written out by hand next to the forward pass it belongs to, because a reader has to be able to follow it.
  • Not a benchmark. Networks here are tens to low thousands of weights. That is not a limitation to apologise for; it is the size at which a network is legible.
  • Not a notebook. No code cells. The controls are the API.

02

Layers, and which way they point

Four packages and an app. Dependencies point one way only, and the reason is testability: everything below apps/web must run under Node in a Vitest file with no DOM, no canvas, and no timers. If it cannot, the visualisation and the algorithm have grown into each other, which is the failure mode this whole layout exists to prevent.

packages/core/   Rng, Float32 helpers, Dataset, split, normalise, metrics
packages/mlp/    layers, init, forward, backward, optimisers, losses, trace
packages/som/    lattice, bmu, neighbourhood, schedules, u-matrix, qe/te
packages/data/   dataset generators — spirals, moons, blobs, colours, iris, digits
apps/web/        Vite app — canvas render, Three.js, workers, panels
server/          ASP.NET Core + SQLite — save/share, slice 15
docs/            this document, the implementation guide, the code guide

           core
          /  |  \
      mlp  som  data       none of these four import each other
          \  |  /
         apps/web          the only place that knows what a canvas is

mlp and som never import one another. They share core's Rng and Dataset, and that is the entire overlap. A shared Trainer abstraction was considered and rejected in about five minutes: the two loops have different inputs, different state, different stopping conditions and different failure modes, and the only thing an abstraction over them could express is that they both have a step function.

Invariants

These must survive between sessions. Breaking one is a bug even when the app still works.

  1. Seeded RNG only. No Math.random() anywhere in packages/. Weight initialisation, batch shuffling, dropout masks and dataset generation all draw from an Rng instance threaded through as a parameter. This is what makes runs reproducible and the golden test possible.
  2. Fixed step granularity. Training advances in whole minibatch steps. The render loop drains steps that have completed; it never trains "for a frame". The same rule as Evolab's fixed physics timestep, for the same reason — a loop that does variable work per frame produces a different answer on a different machine.
  3. Weights are flat Float32Array, row-major, owned by their layer. No arrays of neuron objects, no nested arrays. Three consequences, all wanted: they post to a worker without a structured clone, the renderer indexes them directly, and a whole network serialises as one buffer.
  4. Packages stay pure. No DOM, no window, no timers, no I/O, no console. If something needs to report progress it takes a callback.
  5. Nothing browser-specific below apps/web. Workers, canvas, Three.js, storage, URL parsing — all live in the app.
  6. No autodiff, and no library that provides one. This is the load-bearing decision of the whole project and it is discussed in §12. A hand-written backward pass is the artefact being taught.
  7. Tests are never deleted or loosened to make a change pass. If one fails, either the change is wrong or the change is deliberate — say which, in the commit message, and update the expected value in the same commit.

Two tests that are not like the others

Every project has unit tests. Two here do a different job and neither is optional.

Gradient check

packages/mlp/__tests__/gradcheck.test.ts

For every layer type and every activation, compare the analytic gradient against a central finite difference at h = 1e-4, on a fixed seed, and require agreement to a relative 1e-5.

This exists because a wrong gradient still trains. A sign error in one term or a missing transpose typically slows learning rather than stopping it, so the loss curve still goes down and nothing looks broken. Finite differences do not care how plausible the curve looks.

Golden run

packages/mlp/__tests__/golden.test.ts

Seed 4417, two-moons at 240 samples, 2–8–8–2 with tanh, SGD at 0.1, batch 16, 400 steps. Pin the final training loss to four decimals and the final weight checksum to one integer.

Gradient check proves the maths is right. This proves it is unchanged. Refactoring the inner loop is safe exactly when this number does not move, and every "harmless" tidy-up gets checked against it.

03

What is actually being learned

The perceptron kernel

A network is an array of dense layers. Each layer owns two buffers and nothing else.

interface Dense {
  readonly inputs: number;
  readonly units: number;
  readonly act: 'relu' | 'tanh' | 'sigmoid' | 'linear' | 'softmax';
  W: Float32Array;   // units * inputs, row-major: W[u * inputs + i]
  b: Float32Array;   // units
}

interface Net {
  readonly layers: Dense[];
  readonly loss: 'mse' | 'crossEntropy';
}

Row-major with the unit as the outer index is chosen so that the forward pass walks W linearly — one unit's weights are contiguous — and so that the weight-matrix heatmap in §7 is a straight ImageData blit with no transpose.

The backward pass is written as its own function per activation, immediately below the forward one, sharing the file and the naming. There is no Layer class with a virtual backward(): the whole point is that a reader can put a finger on dz = da * (1 - a * a) and see it is the derivative of tanh.

Optimisers are plain functions over a layer's buffers plus their own state: SGD, SGD with momentum, Adam. Adam is in from slice 7 rather than later because its bias-correction terms are the classic "it still trains, it is just wrong" bug, and the gradient check does not catch optimiser bugs — a dedicated test compares one Adam step against a hand-computed value.

The Kohonen kernel

interface Som {
  readonly cols: number; readonly rows: number;
  readonly dim: number;                // input dimensionality
  readonly topology: 'hex' | 'rect';   // hex is the default — see below
  W: Float32Array;                     // cols * rows * dim, node-major
  hits: Int32Array;                    // samples won, per node
  /** Neighbour indices per node, built once per topology. Never derived inline. */
  neighbours: Int32Array;             // cols * rows * 6, -1 where the lattice ends
}

interface Schedule {
  readonly alpha0: number; readonly sigma0: number;
  readonly decay: 'exponential' | 'linear' | 'inverse';
  readonly steps: number;              // the horizon both decays are written against
}

One step is: draw a sample, find the best matching unit by squared Euclidean distance over all nodes, then move every node toward the sample by α(t) · h(d, t), where d is the distance in the lattice, not in the data. That distinction is the whole algorithm and the UI is built to make it unmissable — §8's SOM stepper draws the lattice neighbourhood and the input space side by side.

The lattice is hexagonal by default, and that is not decoration. On a rectangular lattice a node has four neighbours at distance 1 and four more at √2, so h(d, t) pulls harder along the axes than along the diagonals and the map contracts anisotropically. Hex gives six neighbours all at distance 1 and a genuinely circular neighbourhood. Rectangular stays selectable, because putting the two side by side is itself a lesson.

The consequence to design around: lattice distance is not Euclidean on (col, row). Offset rows have to be converted to axial coordinates before measuring, and getting that wrong makes every neighbourhood subtly the wrong shape on alternate rows — a map that still trains, still looks plausible, and is quietly not a SOM. That is why neighbours is a table built once per topology and tested against a hand-counted 3 × 3, rather than a distance computed inline wherever it is needed.

Both decays are written against an explicit steps horizon rather than a per-step multiplier. A multiplier makes "how fast does it cool" depend on how long you happen to run, which is exactly the confusion challenge 10 exists to create deliberately.

Measuring a map that nobody labelled

  • Quantisation error — mean distance from a sample to its BMU. Goes down as the map fits the data. Charted per epoch, the SOM's answer to a loss curve.
  • Topographic error — the fraction of samples whose best and second-best nodes are not lattice neighbours. This is the number that catches a twisted map, and it is the one a loss curve cannot see. Watch challenge 10 drive QE down while TE climbs.
  • U-matrix — for each node, the mean distance to its lattice neighbours. Drawn as a heatmap it shows ridges where the data has gaps, which is cluster structure recovered without a single label.
  • Component planes — one heatmap per input dimension, showing how that feature varies across the map. This is how a 13-dimensional map becomes readable.
Amendment · slice 9 · built and measured

Quantisation error does not fall below its random-init reading on the colour cube, and that is measured, not a bug. createSom draws weights uniform in [0, 1), deliberately matching the colour cube's own range so a fresh map starts inside the data rather than having to travel to it. That choice means a random map is 144 points drawn from the exact data distribution — an unusually strong quantiser with no structure behind it at all: topographic error at step 0 measures 0.97, essentially every sample's best and second-best nodes unrelated. Training pulls the lattice into a coherent sheet, which costs some of that raw quantising power in exchange for the property a SOM actually promises. Sampling QE at nine checkpoints across a 3 000-step run shows the real shape of it: a spike to 0.36 as soon as topology starts to matter, then a monotonic fall to 0.12 — "goes down as the map fits the data" is true, just measured from after the initial reorganisation rather than from the random start. The golden test pins QE from step 300 rather than step 0 for exactly this reason, and separately asserts the random baseline's own topographic error, so the exception is checked rather than quietly assumed away.

The exponential schedule needed retuning once this was visible. v0 · e⁻¹ remaining at the horizon — the textbook constant — measured visibly under-converged: a 12×12 map still had a higher QE after 3 000 steps than its own random init, because σ was still 2.2 hex-units wide at the final step, wide enough to keep the lattice smoothed together rather than letting individual nodes settle onto the data. Retuned to v0 · e⁻³ (about 5% remaining), which is what the golden numbers are pinned against. The linear and inverse decays were unaffected — linear already reaches its floor at the horizon by construction, and inverse's v0/2 at the horizon was never the textbook constant to begin with.

A step is one sample, not a minibatch — the MLP batches because a gradient is an average over rows, and a SOM update has no such average to take. Samples are drawn with replacement, the classical Kohonen loop, rather than a shuffled epoch: tying "how many times has this row been seen" to the row count would fight the schedule's own steps horizon. Invariant 2's actual rule — training advances in whole, fixed units of work — holds regardless of what the unit is.

Built pure and headless, exactly as far as slice 9 was scoped. No app wiring, no Explorer panel, no network switch yet — net-som's disabled button is corrected to say so rather than left naming a slice number now in the past. npm run som plays the role scripts/train.ts played through slice 2: a golden run pinned in a test, replayed headlessly, printed where a reader can see it — here as two 12×12 grids of real 24-bit terminal colour, before training (scattered noise) and after (a smooth gradient across the lattice), the same evidentiary role scripts/data.ts's ASCII scatter has played since slice 0.

04

Determinism, scoped to what it is for

The golden test and the "reopen a saved run" feature both assume a run replays. It is worth being exact about how far that assumption reaches, because the honest answer is narrower than it looks and finding out later would be expensive.

  • What is exactly specified. IEEE-754 + − × ÷ and Math.sqrt are correctly rounded and identical on every conforming engine. A dot product therefore reproduces bit-for-bit, provided the loop order is fixed — which invariant 3's flat row-major layout guarantees.
  • What is not. Math.exp, Math.tanh, Math.log and Math.pow are implementation-defined in ECMAScript. V8, SpiderMonkey and JavaScriptCore may differ in the last unit in the last place, and V8 has changed its own implementation between versions.
So determinism is scoped to one engine. A run replays bit-identically on the same browser and version. The golden test runs under Node in CI, where the engine is pinned, and its comment says all of this so that the first person to see a browser disagree in the fifth decimal does not go looking for a bug in backprop.

The alternative — shipping our own polynomial exp and tanh — was considered and rejected. It would buy cross-engine reproducibility for a project where nobody is comparing two browsers, at the cost of putting an approximation nobody can check between the reader and the activation function they came here to understand.

Float32 storage, Float64 accumulation

Weights are stored as Float32Array and every intermediate is a plain JavaScript number, which is a double. So a dot product accumulates at full double precision and rounds once on store. This is deliberate and it is what the mainstream frameworks do; the alternative, rounding after every multiply–add, would be both slower and less accurate.

Amendment · slice 2 · what "intermediate" means

This section always said every intermediate is a double, and slice 1 nonetheless stored the per-layer activations in a Float32Array — reading invariant 3 as "float32 everywhere" when it is specifically about weights, which are state and get transferred. Activations are not state; nothing posts them anywhere.

It cost more than it looks. Rounding twice per layer put roughly 1e-7 of relative noise on the loss, which put a floor of 2.5e-3 under the slice-2 gradient check — small enough to look like a subtly wrong gradient rather than a measurement limit, and the backward pass was in fact perfect. As doubles the same check agrees to 9.5e-10. Scratch and gradient buffers are Float64Array; W and b stay Float32Array.

The consequence to remember: W[i] += dw on a Float32Array rounds. Very small updates — a learning rate of 1e−7 against a weight near 1 — are silently lost, because the increment falls below the ULP. That is a real effect, it is a good lesson, and challenge 4 puts a reader in front of it with a diagnostic that names it rather than leaving them to conclude the app is broken.

05

Two threads, and what crosses between them

Training runs in one Web Worker. The main thread renders and never trains — not even one step, not even while paused, because a training call on the main thread is a dropped frame and the fixed-step invariant then has two implementations.

Evolab needed four workers because a genetic algorithm is embarrassingly parallel. Nothing here is: gradient descent is a sequential chain, and a 2–16–16–2 network is small enough that the interesting bottleneck is not arithmetic at all. One worker, and the second core goes to the renderer.

type ToWorker =
  | { type: 'init';  setup: TrainSetup }
  | { type: 'run';   untilStep: number }
  | { type: 'pause' }
  | { type: 'trace'; requestId: number; sampleIndex: number }   // one stepper frame
  | { type: 'probe'; requestId: number; res: number }           // decision field
  | { type: 'poke';  layer: number; index: number; value: number }

type FromWorker =
  | { type: 'ready';  initMs: number }
  | { type: 'step';   metrics: StepMetrics; weights: Float32Array; diag: Diagnostics }
  | { type: 'trace';  requestId: number; frames: TraceFrame[] }
  | { type: 'probe';  requestId: number; res: number; field: Float32Array }
  | { type: 'paused'; step: number }
  | { type: 'error';  message: string }

What gets copied and what gets transferred

Evolab transferred everything, because its payload was a 576-cell archive that it could not afford to clone. Here the arithmetic points the other way for one message and the same way for the other, so the rule is stated per message rather than adopted wholesale:

  • Weights are copied. A 2–16–16–2 network is 354 floats — 1.4 kB. Even a 64–128–128–10 network is 26 k floats, 106 kB. A transfer would detach the worker's own buffer, so the worker would have to allocate a fresh copy anyway; delta-encoding would cost more code than the copy costs bandwidth. The worker posts the whole vector, and reports are throttled to about 20 Hz rather than sent every step, because at 4000 steps/s nothing on screen can consume them.
  • The decision field is transferred. At 128 × 128 it is 16 384 floats, and it is regenerated from scratch every time, so the worker has no use for the buffer after posting. This is the one place the transfer list is worth the care.

Amendment · slice 3 · measured

The field is four to six times cheaper than the table above. Built and timed in the browser: 64² costs 2.6 ms against an estimated 9, and 128² costs 5.6 ms against an estimated 35. The 150 M MAC/s figure was too pessimistic — V8 does considerably better on a loop this shape.

The throughput cost is real but modest. 12 274 steps/s with the field on against 15 083 without, on 2-8-8-2 — about 19%. So §13's "the field will fight the training loop" happened, and did not need the escape hatch that section proposed.

256² is therefore viable on pause rather than export-only. The ladder is left at 64/128 because nothing yet needs the detail, and a resolution nobody asked for is 21 M multiply–adds nobody asked for.

The SOM half needs no worker at all by this arithmetic. It gets one anyway, so that the pause/step/trace protocol has exactly one implementation and the stepper does not become two different mechanisms wearing the same button.

Amendment · slice 4 · built and measured

Moving training off the main thread is worth 88% on the same run. Spirals, 20 000 steps at 2-16-16-2: 6 377 steps/s on the main thread in slice 3 against 11 960 in the worker. Moons at the same shape reaches 28 500. The decision field costs what it always did, but it now costs the worker's time rather than the renderer's, so nothing on screen stutters while it is drawn.

Two message-ordering bugs, and both were races rather than logic. A rebuild does not cancel messages already in flight: pressing Train during one sent run against a session the page had discarded, and a report arriving after one applied the previous network's weights to the rebuilt mirror. The second threw weight buffer is 114, expected 354 only because the architecture had changed as well — a rebuild that changes only the dataset keeps the shape, and there it would have applied cleanly and been silently wrong. Every session carries a generation now, echoed on every message. This is the rule the stepper's trace has to follow in slice 5.

The protocol table above is otherwise as built, including the copy/transfer split: weights are copied both ways, and the field is the one payload that transfers.

Consequence worth stating

Reports at 20 Hz mean the loss chart is sampled, not complete — at 4000 steps/s it draws one point in two hundred. Per-step loss is therefore accumulated in the worker and posted as a min/mean/max band, not as a single sampled value. A chart that samples a noisy series and draws it as a line is a chart that invents smoothness the run did not have, and minibatch loss is very noisy.

06

Teaching by instrument

Two stages of the same application, switched in the toolbar, nothing locked in either direction. A stage decides which panels are present — data-stage on <body>, .guided-hide and .guided-only in CSS — and nothing else. Switching never restarts a run. A planned third stage, Lab, is retired below — it never had content that needed to differ from Explorer.

Guided

the first ten seconds

One flow per network, four steps each, no hyperparameters at all. The perceptron's: pick data, pick a shape, watch it learn, see what changed — ending by replaying its very first guess against its last. The map's: pick data, watch a flat sheet fold into it, see what it kept apart, label it.

Explorer

the working surface

Full controls, the architecture editor and its parameter budget, the diagnostics column, the decision field, the challenge track. This is where somebody spends an hour — the only stage past Guided there is.

Decided · slice 8

Two stages, not three. Lab is retired. The original three-card split gave Lab the architecture editor, optimiser internals, gradient statistics, weight matrices and throughput counters — everything that sounded like it needed its own workbench before any of it existed. By slice 8 all of it had landed in Explorer instead (diagnostics in slice 7, the parameter budget in slice 8), on the same reasoning each time: nothing about the feature actually needed a separate stage to differ from Explorer, so gating one would have meant inventing a distinction that did not exist. The toolbar button and the lab value of AppStage are gone; a bookmarked ?stage=lab link still opens, downgraded to Explorer rather than rejected, the same defensive-URL rule §12 states for every other query parameter.

Amendment · slice 10 · built and measured

The Kohonen switch has a real Explorer behind it, built the same way Guided and Explorer already were: two DOM trees in the same grid cells, gated by body[data-net] instead of body[data-stage], neither ever destroyed by switching. The lattice draws hex or rect with nodes filled by their own weight vector, a QE/TE chart, the U-matrix and component planes as ImageData blits — the same technique §7's table already named for them — and controls for dataset, lattice size, topology and schedule.

Trained on the main thread, and measured before deciding that, not assumed. A SOM step has no backward pass, and benchmarks at roughly 240 000 steps/s on a 12×12 map — about twenty times the MLP's own pre-worker throughput, and fast enough that a full 20 000-step run finishes in under 100 ms of raw compute. Nothing here would be bought back by a worker; the visible pacing (a run organising over about two seconds regardless of its step count) is a fixed 120-tick schedule, not a performance constraint.

That decision re-triggered slice 3's exact bug, and running it live is what caught it. The first version paced ticks with requestAnimationFrame, which does not fire in a hidden tab — precisely the limitation slice 4's worker exists to escape for the MLP, reintroduced here by choosing not to build one. Fixed by switching to setTimeout, throttled rather than suspended in the background: a run paces slower while nobody is watching and still finishes, rather than never finishing at all.

Two smaller bugs, both found the same way — running it rather than reading it back. The "finished" render ran one step early: running was cleared after the pump's own final render rather than before it, so the last frame of a completed run painted with the Train button still reading "Pause". The lattice canvas was invisible at its actual size: resize() measures a canvas's CSS box, and the rule giving #stage/#graph width/height: 100% was scoped to those two ids specifically, so a new canvas id defaulted to the browser's 300×150 and drew correctly into a box a tenth the size of its panel. Neither is the kind of bug a test catches; both were caught by looking at the screen.

SOM datasets are mostly the MLP's own generators, reused unsupervised — moons, circles, blobs, spirals and XOR all already produce a Dataset, and a SOM simply never reads y, so five new generators were not needed to give the picker real variety beside the colour cube. Weight-to-colour is literal at three dimensions and a documented mid-tone stand-in below it; nothing in the current roster exceeds three, so a real projection is deferred rather than built against no data that needs it yet.

The stepper

The teaching screen, and the single most important thing in the project. A full-screen view that pauses the algorithm between operators and shows each one acting on real values.

It drives trainStep(net, batch, { trace: {...} }) — the same function the worker drains at full speed. A test asserts that traced and untraced runs produce bit-identical weights, because the moment that stops being true the screen becomes a lie. This is Evolab's rule, lifted intact, and it is the reason the trace flag lives inside the kernel rather than in a parallel "explain" implementation.

Amendment · slice 5 · built and measured

One trace covers a whole step, not one operator. Stepping through the stages is a client-side cursor into a single StepTrace — forward through every layer, backward through every layer, the update already applied — rather than a re-run of the network one layer at a time. A new trace is only requested from the worker when the reader pages past the last stage of the one on screen.

The output layer's backward step has no stage of its own. Under softmax + cross-entropy the Jacobian cancels and dz = a − onehot(target) directly — the one place in backprop where the chain rule does not appear as two visible factors. So for 2-8-8-2 the count is seven stages, not the eight "forward × 3, backward × 3, update" would suggest: sample, forward × 2, output-and-loss (which folds in that fused backward step), backward × 2, update. The screen says why, rather than leaving a reader hunting for a δ × a′ that was never computed.

Verified live: the golden run reached its pinned 0.1007 / 0.9702 / 38 epochs after two stepper steps had run at the start of the same session, and a test runs 200 traced steps against 200 untraced from the same seed and checks every weight agrees exactly.

MLP — seven stages

sample → forward × n → loss → backward × n → update

One sample at a time. Each forward stage shows the layer's weight row, the pre-activation z, and the activation a. Each backward stage shows δ arriving, the local derivative, and δ leaving. The update stage shows Δw per weight with the learning rate applied and the sign coloured.

SOM — five stages

sample → distances → BMU → neighbourhood → update

Distances shown as the lattice heat-mapped by ‖x − w‖. BMU marked. The neighbourhood stage draws h(d,t) falling off across the lattice with the current σ printed, and the update stage shows every node's movement as a vector in input space, scaled by its own h.

Amendment · slice 11 · built and measured

No worker round trip, because slice 10 already found there is nothing on the other side of one. The MLP stepper requests a trace and waits for onTrace; the SOM stepper calls somStep(trainer, ds, { trace: true }) directly and reads the result synchronously. SomStepTrace is built inside somStep rather than by a sibling function, because the per-node loop the update already runs is the same loop that has to visit every node to report a distance and a strength — splitting it would either duplicate the loop or force an awkward second pass. A test proves tracing changes nothing: 200 traced steps and 200 untraced steps from the same seed land on bit-identical weights.

Two pictures, not one, and neither alone is the algorithm. The lattice view is built exactly as this section specifies. Beside it, an input-space view — every node's weight vector as a point, connected to its lattice neighbours by a line, the net the map actually is, drawn where the data lives rather than where the nodes sit on screen. Built once, in render/inputspace.ts, rather than as a stepper-only view: the guided flow's own step 2 ("watch a flat sheet fold into it") is the identical drawing at a different moment, and building it twice was never on the table.

Amendment · slice 2 · cards 1 and 3

Two of these cards described an outcome the build does not produce. Both were corrected against measurements rather than reasoning, and both turned out to teach something better than the version written here first.

Card 1 said a flat network cannot beat chance on XOR. The linear ceiling is 75%, not 50%. A line can isolate one quadrant — say (+, +) — and answer "the other class" everywhere else, which is right for three quadrants out of four. Measured across seven split seeds the flat network lands between 0.29 and 0.77 and never higher; one hidden layer reaches 1.0000. So the card now says it gets three quarters of them and can never get the last quarter, however long you train it, which is both true and a sharper statement of what a missing hidden layer costs.

Card 3 said the loss goes to NaN at a learning rate of 3.0. Neither half is right. With tanh hidden units, a softmax output and cross-entropy, every factor in the gradient is bounded — |a − y| ≤ 1, tanh′ ≤ 1, |a| ≤ 1 — so the weights grow linearly with the learning rate and never overflow. Measured over 400 steps on two moons: lr 3 reaches 0.988 accuracy, better than lr 0.1; lr 10 falls to 0.744; lr 500 collapses to 0.500 with a loss of 13.8 and max |w| of 1.4e4 — without a single non-finite number anywhere.

The learning-rate control therefore runs to 500 rather than to 3, and the card's outcome is the accuracy collapses to chance and the loss stops falling. §7's max-shift is what makes that legible instead of blank: at those weights the logits reach 1e5, and an unshifted exp would fill every panel with NaN. Diverging is the lesson; NaN everywhere would be a bug.

Explanations that cannot rot

Every card ends with an afterword, and afterwords are data that branches on the outcome, never fixed strings. A card that asserts "the loss diverged" when it happened not to teaches the reader to stop reading. Card 3 is the sharp case: at lr 3.0 the loss usually goes to NaN and occasionally just oscillates, so its afterword has two branches, and a test renders both against synthetic outcomes and asserts the non-divergent branch does not use the word.

The same rule one level up: help text is generated from the data it describes. The shortcut list comes from ui/keymap.ts, the challenge summaries from the card definitions, the dataset descriptions from packages/data. Anything a human retypes is a second description that rots.

Amendment · slice 7 · built and measured

Histograms and gradient flow built exactly as specified above — 32 fixed bins, rects, log scale for the gradient bars, one row in the drawing table and not two, because a weight histogram and an activation histogram are the same picture of a different array. What §7 did not yet say is who owns the array: activationStats runs forward once per training row, and doing that into the same scratch buffer the network graph reads for the probe's node colours would leave the graph painting the last diagnostics sample instead of the point under the reader's cursor. A dedicated diagScratch, rebuilt alongside the network, is the third buffer in this project built for exactly that reason — evaluateRows and the stepper's trace scratch were the first two.

Dead-unit counting turns challenge 5 from a claim into a live number. A unit counts as dead if it never fires positive across the whole training set — not the probe point alone, since a unit dead at the probe might fire elsewhere. Forcing zero initialisation under a ReLU stack reads 16 of 16 dead before the first step runs; the same network trained with Adam for 400 steps reads 0 of 16. Only ReLU layers are counted — tanh and sigmoid units are never "dead" in this sense, so the readout says no relu layers rather than a misleading zero.

Switching optimiser mid-run needed its own reset boundary. Momentum and Adam each carry state across steps — a velocity, or a pair of moments — and a plain config assignment would let Adam's second moment survive under Momentum's label after a switch, silently wrong rather than reset, and it would still train because a mislabelled velocity is still a velocity. setTrainConfig compares the incoming optimiser kind against the current one and resets only on an actual change; it is the one path both the page and the worker's case 'config' use, replacing what had been a bare assignment on the worker side.

Momentum is written as the unscaled v ← β·v + g, not the exponential-moving-average form some texts use — deliberately, so it reads as a visibly different convention from Adam's actual EMA sitting in the same file, rather than the same idea written twice with a silent factor of (1 − β) between them. Adam is checked two ways, per the risk register entry below: a hand-computed first step, and a closed-form identity — for a constant gradient, the bias-corrected moments converge to exactly g and g² at every step, so the effective step size is exactly the learning rate regardless of magnitude, which a convergence-only test would not catch a violation of.

The 3D views, and the rule they live under

A 2D / 3D toggle in the toolbar, or 2 and 3. Two scenes, one per network, both dynamically imported.

  • MLP — the loss surface. A height field of the loss over two directions in weight space, with the optimiser's actual path traced across it and the current position marked. The obvious implementation — pick two named weights and vary them — produces a boring bowl, because two weights out of 354 barely move the loss. The one that produces the famous pictures is two random directions, filter-normalised (Li et al., 2018): draw two random vectors in full weight space, rescale each layer's slice to match the norm of the corresponding slice of the real weights, and evaluate on that plane. A dropdown offers both, with the named-weights mode labelled literal and the random mode labelled representative, because the difference between them is itself the lesson.
  • SOM — the lattice folding. Nodes drawn at their weight vectors in input space, connected by their lattice edges, floating in the data cloud. For dim 3 this is exact. Above 3 it is a projection, and the projection is named on screen — PCA on the data, not on the weights, so the view does not change as the map moves. Watching a flat sheet fold itself through a data cloud is the best thirty seconds in the whole project.
3D is a view, never the simulation. The maths is identical in both; the drawing is all that changes. 2D stays the default and the teaching surface, and no feature may exist in 3D that the 2D view lacks. Evolab learned this the expensive way — its 3D replay of a 2D physics engine had to have three sections of its design document amended — and the rule is inherited rather than rediscovered.

Amendment · slice 12 · built and measured

The loss surface and its path share one flat-weight-space kernel with the run's own weight buffers, not a parallel notion of "direction". A direction is exactly a Float32Array the same shape flattenWeights/applyWeights already use, so projecting a snapshot onto one is a plain dot product and evaluating the surface is applyWeights into a scratch network followed by forward. Nothing perturbs the real network — checked by a test asserting its weights are byte-identical before and after a surface is computed — and the arithmetic itself is checked against a hand-worked closed form: a 1-1 linear network with mse loss has loss(w, b) = 0.5·(wx + b − 1)², worked out on paper and matched to a 3×3 grid exactly, the same discipline slice 9's lattice table used for a discrete structure applied here to a continuous one.

Literal and representative modes produce measurably different pictures, verified live rather than merely asserted. On the trained golden run, representative mode's path — projected onto two random directions — stays visibly short near the current-position marker. Switching to literal mode on the same trained network, without retraining, shows a path several times longer: an individual weight's own trajectory correlates with itself in a way a random projection of 114 dimensions mostly does not. Both pictures are real: only their honesty about what two dimensions out of many can show differs, which is exactly what §7 asked the comparison to teach.

A custom orbit camera, not three's own OrbitControls addon. Spherical coordinates around a fixed target, updated from pointer and wheel listeners, reset on double-click — about eighty lines, shared by both scenes, and it keeps the dependency surface at the one three package itself rather than also importing from three/examples.

No bug needed fixing to get this working, which is worth recording plainly rather than inventing one to match the pattern of every amendment before it. The one place a mistake was designed around rather than found live: the 2D field's own canvas helper calls canvas.getContext('2d'), which permanently locks a canvas out of ever getting a WebGL context afterward — so the 3D canvases get their own sizing helper, which only ever reads clientWidth/clientHeight, known going in rather than discovered by a crash.

The server, and the rule it lives under

One ASP.NET Core project serving the built SPA at one origin, storing runs in SQLite. It arrives at slice 15 and not before, because it is the familiar comfortable part and it would otherwise serve a client that does not exist.

The app works with no server at all, and that is measured, not asserted. Kill the server mid-session: training continues, no dialog appears, no unhandled rejection is logged, and one amber dot appears in the toolbar. npm run dev and npm test need no .NET; dotnet test needs no Node.

The client wrapper never throws, so there is no try/catch anywhere else in the app. Offline, timeout, 404, 500, an HTML error page from a proxy, and a 200 with unparseable JSON all become one ApiResult union. Five-second AbortController on every request, because a hanging one gives neither an error to report nor a result to use.

EndpointDoesPayload
POST /api/runssave a runconfig + final metrics + seed. No weights.
GET /api/runslist minetitle, network, dataset, final loss, when

Nothing is uploaded because nothing needs to be: a run is deterministic in its seed, architecture, dataset and step count, so reopening one re-trains it. A 400-step run on two moons is roughly 40 ms of arithmetic — cheaper than the round trip that would fetch the weights instead. Two conditions make that true and both are already invariants: the seeded RNG, and the fixed step granularity.

Recorded in advance

Determinism is engine-scoped (§4). A run saved in Chrome and reopened in Firefox will reproduce to about five significant figures, not exactly. So the stored final loss is compared on reopen at a stated tolerance and a mismatch is reported as a note, not an error — and the note names no cause, because a lossy record and an engine difference are equally likely and the app cannot tell them apart.

Why the order is this order

  • Slice 1 has no learning in it at all. Drawing the network and watching activations move is worth a slice on its own, and it means slice 2 debugs backprop against a forward pass already known to be right.
  • The stepper is slice 5, not slice 12. It is the point of the project, and it needs to exist before six more panels are built on assumptions it would have corrected. It also forces the trace machinery into the kernel early, when moving it is still cheap.
  • The SOM starts at slice 9, after the MLP is complete through diagnostics. Both halves share the chassis, the chart, the worker protocol and the stepper frame. Building the second network second means the shared parts are shaped by one real client before they acquire a second, rather than being designed for two hypothetical ones.
  • The guided flow is built twice, and the second time is slice 11. Both networks get one — §13 — but a flow can only be built once there is something to guide somebody through, and the map's third step is the U-matrix. So slice 6 builds the frame plus the perceptron's flow, and slice 11 adds the map's beside the SOM stepper. The frame takes the flow as data from the first version rather than being generalised later: retrofitting a second client onto a hardcoded first one is how the copy ends up duplicated, and duplicated copy is the exact risk §13 named when this was still an open question.
  • 3D is slice 12, after both networks work. It is a view. If it arrived earlier it would grow features, and §7's rule would already be broken.

No machine-learning library

TensorFlow.js, ONNX Runtime Web and brain.js were all considered, and the decision is not close.

  • It would hide the artefact. The backward pass is the thing being taught. A library that computes gradients for you removes precisely the code the reader came to see, and the stepper — the point of the project — would have to reimplement backprop to display it, at which point there are two implementations and one of them is a lie.
  • Pausing between operators is not something a framework offers. fit() is a black box by design. Getting per-layer δ out of a graph executor mid-step means fighting the abstraction the whole way.
  • The size does not need it. TF.js is roughly 900 kB minified with a WebGL backend for networks a thousand times larger than any here. §5's arithmetic puts a training step at 0.1 ms in plain scalar JavaScript.

The cost is real and worth naming: convolutions, recurrence, and anything past a few thousand parameters are out of scope permanently. That is the correct trade for this project, and if it ever stops being correct, the honest move is a second project rather than a dependency.

No React

Evolab reached slice 16 without it and recorded that as a decision rather than a deferral. The argument is stronger here: the panels that matter are canvases, and a canvas is one useEffect and a ref in React and one function call without it. The DOM that does exist is a few hundred controls-and-readouts that are written once and updated by id.

The trigger condition is worth writing down so the decision can be revisited honestly rather than defended: if a panel's DOM ever needs to be reconciled — a list whose items are inserted and removed as data changes, not just retextured — that is the day this gets revisited. The architecture editor in slice 8 is the closest thing to it, and it is a list of at most eight rows that rebuilds wholesale.

Deliberately absent

D3

Every chart here is a path or an ImageData blit on a canvas. D3's value is data-joined SVG, which is exactly the thing §7 says not to do.

A state library

One plain object, panels take what they read. There is one writer — the worker's report handler — and one render pass.

Comlink

Six message types across two unions, and the one thing that needs care is which buffers transfer, which is exactly what an RPC wrapper hides.

What I expect to go wrong

Written before the build, so it can be checked against afterwards. Evolab's equivalent section was more useful than its risk register, because it named specific failures rather than categories.

  • A wrong gradient that still trains. The most likely bug in the project and the hardest to notice, because the loss curve still descends. This is why gradient check is slice 2 and not slice 7, and why it covers every activation rather than one.
  • The decision field will fight the training loop. Both live in one worker and the field costs ninety times a training step. The throttle in §5 is a guess; the number that matters is whether steps/s visibly drops when the field is on, and if it does the field moves to its own worker with a copy of the weights.
  • Someone will report the loss differing between browsers as a bug. §4 exists so the answer is one paragraph rather than an afternoon. The golden test's comment says it too, at the place where the number is pinned.
  • Adam will be subtly wrong. The bias-correction terms are easy to misplace and the loss still goes down without them — just more slowly at the start, which looks like a learning-rate issue. Its own test against a hand-computed step, not a convergence check.
  • Topographic error will be wrong at the lattice edges. Corner nodes have three neighbours on a rectangular lattice and the naive implementation assumes four, which biases TE by roughly the perimeter fraction — about 20% of a 12×12 map. The neighbour table is built once, per topology, and tested against a hand-counted 3×3.
  • The network graph will look worse than the screenshots in my head. 320 overlapping translucent lines is a lot of ink. The mitigation is in §7 and it has a stated trigger; the risk is that the trigger turns out to be 12 units rather than 24, in which case the matrix view is the primary and the graph is the toy.
  • The SOM will look finished before it is. A colour-cube map orders itself beautifully in a few thousand steps and looks like a working implementation with the neighbourhood function subtly wrong. The colour cube is a demo, not a test; the golden QE number and the hand-counted 3×3 neighbour table are the tests.
  • Scope will drift toward a second MLP feature instead of the SOM. Convolutions, dropout, batch norm and learning-rate schedules are all one afternoon each and all more familiar than Kohonen maps. The slice order is the defence, and slice 9 is the line.

Answered

The snapshot ring is capped at 60, in count, not megabytes. The open question was whether an epoch scrubber was worth keeping weights every 20th report, at 106 kB a snapshot — "probably fine, probably needs a cap, and the cap should be stated in steps rather than megabytes." It is: AppState.snapshots keeps exactly 60 regardless of how long the run is, the same "pace by a fixed count, not by run length" rule the SOM's own training pump already used. At 60 snapshots the default 2-8-8-2 network is under 7 kB; the largest network this project will reach (64-128-128-10, slice 16) is under 6.4 MB. One is taken per worker report that closed a chart point, not per report — reports arrive roughly 25 times a second, points at most 200 times a run. The scrubber itself did not arrive with this decision; slice 12 needed the ring for the loss surface's path and built only that.
Hex, and it is the default. Rectangular stays as an option because two topologies side by side is itself a lesson — but a hex lattice is what the literature means by a SOM, and the reason is not aesthetic. On a rectangular lattice a node has four neighbours at distance 1 and four more at distance √2, so the neighbourhood function is anisotropic: the map shrinks faster along the axes than along the diagonals. Hex gives six neighbours all at distance 1, and h(d, t) is then genuinely circular. Since §3's whole claim is that the neighbourhood is a distance in the lattice, the lattice should be one where that distance behaves.

The cost is real and lands in four places, all in slice 9 or 10:

  • Lattice distance stops being Euclidean on (col, row). Offset coordinates have to convert to axial before measuring, or every neighbourhood is subtly the wrong shape on alternate rows. This is the single most likely bug in packages/som and it is the reason the neighbour table is built once, per topology, and tested against a hand-counted 3 × 3 rather than derived inline.
  • Every drawing routine gains an offset row — the lattice, the U-matrix, the component planes and the hit map. They already share one blit path, so this is one change rather than four, but hexagons are not ImageData rectangles and the U-matrix loses its cheapest implementation.
  • Topographic error's neighbour test changes, and §13 already flags that its edge nodes are the easy thing to get wrong. Hex makes the boundary cases different rather than harder: a corner node has three neighbours, an edge node four.
  • The 3D folding view draws hex connectivity, which is six edges per node instead of four — 30% more line work and no structural change.
Two guided flows, and the second one arrives at slice 11 rather than slice 6. A reader who came for Kohonen maps and is handed a perceptron tutorial has been told their question is the less important one, which is the opposite of what §1 claims about the two halves. So both get one.

The slice order changes to match, and the reason is that a guided flow can only be built once there is something to guide someone through:

  • Slice 6 builds the guided framework and the MLP flow. Four steps, the step list, the branching afterwords, the before-and-after replay. The framework takes the flow as data from the start rather than being generalised later, because retrofitting a second client onto a hardcoded first one is how the copy ends up duplicated.
  • Slice 11 adds the SOM flow, beside the SOM stepper — the first point at which the lattice (slice 9) and the U-matrix (slice 10) both exist. Amendment · slice 6 · built and measured

The step metadata and the DOM split further than planned, and it was worth it for a reason unrelated to the flow itself: run/guided.ts holds the four steps, the shape-to-hidden-layer mapping, and the branching afterword as pure functions with no import from the DOM, so it sits in the same vitest glob as camera.ts and trace.ts and is checked under Node. ui/guided.ts is the renderer and is exercised live instead, the same split slice 5 used for the stepper.

Two controls went stale, and it was one bug wearing two costumes. Picking a dataset or a shape in Guided writes state.dataset/state.hidden directly rather than driving the <select> or the preset buttons, so neither control's DOM learned about the change — picking XOR in Guided left Explorer's dropdown reading "Two moons". Fixed centrally in renderDataPanels/ renderNetPanels, which now write every control from state on every call rather than trusting each call site to remember. Three redundant assignments elsewhere were deleted with the fix.

A second bug, found the same way: progress advanced after the render that needed it, not before. pickDataset/pickShape call straight into regenerateData/regenerateNet, which end in a synchronous render() — and that call re-enters the guided panel's own render before either function returns. Advancing the step counter afterwards left the panel painted once with the previous step still marked current, with nothing left to trigger a second paint.

Verified on a run the branching afterword was written for rather than against: XOR with no hidden layer — challenge 1, reachable from Guided precisely because it never says the words "hidden layer" — landed at 47.2% → 44.4%, accuracy that went down. The afterword said so.

The cost that was worrying: two sets of copy to keep true. It is unchanged and it is the thing to watch. The defence is the same one §6 applies to the challenge cards — afterwords are written against live values, and a test renders every branch of both flows against synthetic outcomes.

Amendment · slice 11 · built and measured

"One renderer" turned out to mean something narrower than one function, once there were two state shapes to read. AppState and SomState share nothing; a single controller polymorphic over both would need as many branches as two controllers have lines, which is not the saving the plan imagined. What is genuinely shared — because it is one idea, not two — is the step-card and choice-button vocabulary: pulled out into ui/guidedShared.ts once ui/somGuided.ts needed it a second time, rather than copied. run/guided.ts's GuidedFlow type and its one array per network stand as planned.

Labelling a map is a vote taken after training finishes, never a training signal. nodeLabels has every row's BMU vote for that row's class; a node's label is whichever class won it most, and a node no row ever won reads -1 rather than 0, so "unlabelled" and "labelled class zero" cannot be confused. An unlabelled dataset — the colour cube — returns every node as -1, and the flow says so in plain words rather than drawing an empty grid and leaving a reader to wonder why.

A second render-order bug, the same shape as slice 6's, found the same way. "Reveal labels" was clicked and nothing happened: unlike picking a dataset, revealing labels changes no state a rebuild renders as a side effect, so there was nothing for the click handler to piggyback a render on. Fixed by giving the SOM guided controller its own requestRender callback and calling it explicitly.
